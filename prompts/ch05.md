# ch05｜任務網絡與協作回路

## 這章在講什麼

- 任務之間的依賴不是開工時畫好就不變的「靜態流程圖」；現代協作要把任務看成一張會動態重組的有向無環圖（DAG），讓任務自己告訴系統該跟誰合併、該讓誰先走。
- 每條邊要有兩個權重：「資料依賴度」（兩個任務的資料重疊多少）與「時間窗」（任務多急）。依賴高又不急的可以合併；依賴低又都很急的要分開，免得搶資源。
- 排程要「時間驅動」地重算臨界路徑（書中設定約每 30 秒一次），用增量計算只更新變動處，並把注意力集中在後面掛著一串任務的瓶頸節點。
- 協作回路分三階：微觀是代理之間的確認訊息（收到、理解、開始做），中觀是 Monitor 對結果抽檢（正確性、完整性、一致性），宏觀是人類直接拖曳調整優先級。
- 系統會自然熵增、任務蔓延，需要「熵減」：用 SimHash 指紋去重（漢明距 ≤ 3 視為重複），但只有合併後能省下超過約 15% 總工時才真的合併。
- 反方：回路太長會造成回饋遲滯、過度自動化會讓人失去判斷例外的能力；系統處理常規，人專注例外並保有最終決策權。

## 作者做過的實驗／例子

- 開場：產品分析師等數據團隊的去重結果，訊息是「SimHash 去重完成，漢明距 ≤ 3 合併 2,347 條，節省預估工時 6.2 小時」。
- 資料依賴度例子：兩個團隊分別處理用戶回饋與客戶投訴，系統比對發現重疊 34%，建議合併或共用中間結果。
- 15% 合併門檻的拆解：合併本身耗時約 5～8%、風險成本約 5%、安全邊際約 2～3%；合併穩定的類別可降到 10%。
- 兩個情境推演：市場調查團隊用去重＋依章節依賴調整寫作順序，72 小時內交出報告；災害應急時頻寬縮減，任務網路改成最急的先走、同區域資訊只請求一次、離線先記錄再上傳。

## 教練解說要點

- 「臨界路徑」不是固定的：任何一個節點延遲，最長路徑可能整條換掉，所以要定期重算，而不是等人來催。
- 確認訊息把「以為對方知道」變成「確定對方收到」，還順便留下審計軌跡；抽檢則補上「回覆收到但其實沒看」的漏洞。
- 去重要兩段：先用便宜的指紋快速篩，再判斷值不值得合併；門檻設太低會誤合併、設太高會漏掉。
- 回路每多一層就多一段延遲，五個環節各遲兩小時就是十小時；設計回路時要算總延遲。

## 演練

> 說明：練習視窗工作目錄是 practice/。本書沒有附程式：用 Python 標準庫（不可 pip 安裝任何套件）寫小模擬，檔案放 practice/ch05/interactive/，用 `PYTHONUTF8=1 python ch05/interactive/xxx.py` 執行。需要真實模型時用 practice/llm_agent.py 的 ask／ask_json（走 claude -p），整章最多呼叫 2 次。

### 練習 1：動態 DAG 重算臨界路徑，再用 SimHash 做熵減

**目的**：親手看到「某個節點延遲後臨界路徑換人」，以及「漢明距門檻＋15% 合併收益門檻」如何決定哪些任務該合併。
**送給練習視窗的提示詞**：

```text
寫 ch05/interactive/task_dag_sim.py（只用標準庫，random.seed(5)，不可 input()，30 秒內跑完），輸出只寫在 ch05/interactive/ 底下：
A. 任務 DAG 與臨界路徑：
  1. 建 12 個任務 T01～T12，每個有工時 hours（2～10 隨機整數）；手動定義約 15 條依賴邊（保證無環，用拓撲排序檢查，有環就丟 ValueError）。
  2. 寫 critical_path(dag) 回傳最長路徑與總工時。
  3. 模擬 10 個 tick（代表每 30 秒重算一次）：每個 tick 隨機挑 1 個任務延遲 +1～+4 小時，重算臨界路徑；若路徑上的任務組合跟上一個 tick 不同，標記 CHANGED。
  4. 印一張表：tick｜延遲的任務｜臨界路徑｜總工時｜是否 CHANGED，並印出「被下游依賴最多的前 3 個瓶頸節點」（以可到達的下游任務數計）。
B. 熵減（去重＋合併門檻）：
  1. 自己實作 64 位元 SimHash（用 hashlib.md5 對字元 2-gram 取雜湊），與 hamming(a, b)。
  2. 準備 12 句中文用戶回饋（其中 3 組是換句話說的近似句、2 組只差一兩個字），兩兩算漢明距，≤ 3 視為重複候選。
  3. 對每組候選計算合併收益：saved = 較小任務工時 × 重疊比例，cost = 合併成本 6% ＋ 風險 5% 乘以兩者總工時；只有 (saved - cost) / 兩者總工時 > 15% 才合併。
  4. 印出：候選對｜漢明距｜收益百分比｜MERGE／SKIP，並把門檻改成 10% 再跑一次，比較合併數量差異。
最後把兩段結果存成 ch05/interactive/task_dag_report.md。
```

**觀察重點**：

- 至少出現一次 CHANGED：延遲落在非臨界節點時總工時不變，落在臨界節點或讓支線變長時路徑會換掉。
- 只差一兩個字的句子漢明距很小；換句話說的近似句漢明距往往 > 3，正好說明書中「指紋粗篩之後還要語義判斷」。
- 門檻從 15% 降到 10%，合併數只會增加不會減少；若反過來代表收益公式寫錯。

### 練習 2：真實模型扮演下游代理，回覆交接確認訊息

**目的**：讓真實模型扮演收到上游交接的下游代理，檢查它的確認訊息是否具備「收到／理解／開始做」三個節點，並能在交接資料殘缺時當場回報，而不是默默開工。
**送給練習視窗的提示詞**：

```text
寫 ch05/interactive/handoff_ack.py（只用標準庫＋practice/llm_agent.py；檔案開頭用 Path(__file__).resolve().parents[2] 把 practice/ 加進 sys.path 再 from llm_agent import ask_json）：
1. 準備一份上游交接 payload（dict）：任務「整理兩萬條用戶回饋的去重結果」，欄位 task_id、merged_count=2347、saved_hours=6.2、source_files 清單；故意漏掉 deadline，並讓 source_files 列 3 個檔、但 file_count 寫 4。
2. 用 ask_json 呼叫 claude -p 一次：請它扮演下游「報告撰寫代理」，收到這份交接後只回 JSON：
   {"received": true/false, "understood": "一句話複述任務", "integrity_check": "pass|fail", "issues": ["..."], "start_now": true/false}
3. 用程式規則判定並印出表格：
   - 三節點齊全：received、understood（非空）、start_now 都存在 → PASS／FAIL
   - 有沒有抓到 deadline 缺漏、有沒有抓到 file_count 不一致（在 issues 文字中搜尋關鍵字）
   - 若 integrity_check 為 fail 卻 start_now 為 true，判為「帶傷開工」違規
4. 再加一段 Monitor 抽檢模擬（不呼叫模型）：random.seed(55)，產生 200 筆假交接，每筆有 8% 機率內容錯誤；抽檢率 10% 與 30% 各跑一次，印出抽到幾筆、抓到幾個錯、估計錯誤率；接著模擬「某團隊失敗率高就把抽檢率提高到 50%」的規則。
5. 結果存成 ch05/interactive/handoff_ack.md：模型原始 JSON、逐條判定、抽檢表，以及一段說明：為什麼不能只看對方回了「收到」。claude -p 只呼叫 1 次。
```

**觀察重點**：

- 模型是否兩個缺陷都抓到？抓到後是否還想 start_now？（每次結果可能不同，照實記錄）
- 抽檢率越高抓到的錯越多，但估計錯誤率應都落在 8% 附近；抽太少時估計值會跳動很大。
- 結論是否講到微觀確認只保證「有溝通」，品質要靠中觀抽檢補。
